## Critical

### C1. Product images ship 28.7 MB on a single page

> **This is a data-cost defect, not a Core Web Vitals defect.** Lighthouse's performance score is a blend of FCP, Speed Index, LCP, TBT and CLS — total bytes is not among them, and "Properly size images" appears only under Opportunities, which carry zero scoring weight. Expect PageSpeed Insights to score this page well regardless. The images are below the fold and are not the LCP element. Fix it for the reasons below, not to move a Lighthouse number.
>
> Measured transfer times for the 28.7 MB: 9.2s on fixed LTE (~25 Mbps), **19.2s on typical SA 4G (~12 Mbps)**, 57.5s on congested 4G. Cost to the visitor: **R2.39 per page view** on an R85 prepaid 1 GB bundle, R0.84 on contract data at R30/GB.

Verified by direct HTTP HEAD against production:

| File | Dimensions | Weight | Rendered box |
|---|---|---|---|
| `learniq.png` | 2816×1536 | 8.34 MB | 192 px tall (`h-48`) |
| `nomadiq.png` | 2816×1536 | 8.22 MB | 192 px tall |
| `vendiq.png` | 2816×1536 | 6.52 MB | 192 px tall |
| `voltiq.png` | 2816×1536 | 5.68 MB | 192 px tall |

Total 28.7 MB, against roughly 126 KB for the entire rest of the page. Each file is duplicated in `design/images/` and `site/images/`, so approximately 57 MB sits in git.

No `loading="lazy"`, no `width`/`height`:

```html
<img src="images/nomadiq.png" alt="NomadIQ - Digital Nomad Visa Automation" class="w-full h-full object-cover"/>
```

This matters disproportionately for a South African audience paying mobile data rates.

**This violates your own written standard.** [docs/web-standards.md](web-standards.md) sets explicit budgets and rules that these four files break:

| Rule in `web-standards.md` | Budget | Actual |
|---|---|---|
| Full-width images | under 100 KB | 5.68-8.34 MB |
| Avatar images (48×48 WebP) | under 2 KB | 158-242 KB (see C1b) |
| Total page payload (mobile) | under 2 MB | ~28.9 MB on `products.html` |
| Below-fold images MUST have `loading="lazy"` | required | absent on all four |
| `<img>` MUST have explicit `width`/`height` | required | absent on all four |
| Raster images MUST use `<picture>` + WebP with JPG fallback | required | absent on all four |

**The reference implementation is already committed**, three cards away in the same file at `site/products.html:198`:

```html
<picture>
<source srcset="images/socialiq.webp" type="image/webp"/>
<img src="images/socialiq.jpg" alt="SocialIQ - Social Media Writer" class="w-full h-full object-cover" width="1200" height="1200" loading="lazy"/>
</picture>
```

SocialIQ conforms at 0.06 MB. The four PNGs are the outlier, not the convention. A prior session already logged this in `CHECKPOINT.md`; it has not been actioned.

- **First principle:** bytes delivered must be proportional to pixels displayed. A 4.3-megapixel image in a 192 px box violates this by 20-40x.
- **Blocks:** all meaningful mobile performance work.
- **How would we know this failed?** After conversion, `curl -sI` on each image should report under ~100 KB. If PSI still flags "Properly size images" on `products.html`, it did not land.
- **Leading indicator:** total `products.html` transfer weight.

Recommended: resize to ~1300 px wide, convert to WebP or AVIF, add explicit `width`/`height`, add `loading="lazy"` to the three below-fold cards. Estimated 28.7 MB → under 400 KB.

### C1b. Homepage testimonial avatars are 1.31 MB

Seven headshots at 158-242 KB each, source files **1024×1024**, rendered at **48×48**. Roughly 450x more pixels than displayed.

Unlike C1, the markup here is correct — every one carries `width="48" height="48"` and `loading="lazy"`:

```html
<img src="images/lerato-m.jpg" alt="Lerato M." class="w-12 h-12 rounded-full object-cover" width="48" height="48" loading="lazy"/>
```

Only the source files are wrong. Because they are lazy-loaded and below the fold, they do not affect the homepage Lighthouse score — which is why the homepage tests well despite carrying them.

[docs/web-standards.md](web-standards.md) is explicit here: *"Avatar images (48x48 WebP) — Under 2KB each."* At 158-242 KB these are roughly **100x over your own budget**, and they are missing the required `<picture>` + WebP treatment. Meeting the standard takes 1.31 MB down to **under 14 KB for all seven**.

- **How would we know this failed?** `curl -sI` on each avatar returns 2 KB or less.

## High

### H1. Root robots.txt is 404, and the deployed one is inert

- `https://digitaloperations.co.za/robots.txt` → **404**
- `https://digitaloperations.co.za/doqix/robots.txt` → **200**

Per RFC 9309 §2.3, robots.txt is only recognised at the origin root. No crawler ever requests `/doqix/robots.txt` as a directive file. Two consequences:

- `Disallow: /doqix/thank-you.html` has **zero effect**. (That page is nonetheless correctly protected by its own `noindex,nofollow` meta tag, which is what is actually doing the work.)
- `Sitemap: .../doqix/sitemap.xml` has **zero effect** for discovery.

**Root cause, traced across repos:** the apex is served by `StephanM-ZA/stephanm-za.github.io`, containing only `CNAME` and a meta-refresh `index.html` (verified). The `doqix` repo is a project page nested at `/doqix/` and cannot write to root `/robots.txt`.

**Discovery-path matrix:**

| Path | Working? |
|---|---|
| Root robots.txt `Sitemap:` | **No** — root is 404 |
| Google Search Console submission | Ownership verified (`google-site-verification` meta present); actual submission not verifiable outside the GSC UI |
| IndexNow (Bing, Yandex, Seznam, Naver) | **Yes** — key file live, CI step present, `keyLocation` correctly set to the subpath. Google does not participate. |
| Internal link to sitemap | Not present |

Google has exactly one discovery channel, and it is manual.

**Fix requires a commit to a different repository** (`stephanm-za.github.io`), outside this project's scope.

### H2. Internal navigation is invisible without JavaScript

Verified against raw, unexecuted HTML:

| Page | Outbound `.html` links in raw HTML |
|---|---|
| `index.html` | `contact.html` **only** |
| `products.html` | `contact.html`, `services.html` |
| `services.html` | `contact.html` |
| `contact.html` | `privacy-policy.html` |

The homepage contains **zero** references to `products.html` or `services.html`. Both nav and footer are client-injected:

```html
<div id="site-header"></div><script src="js/header.js?v=0.12.10">
<div id="site-footer"></div><script defer src="js/footer.js?v=0.12.10">
```

`render_page.py` confirms `is_spa: false` — body copy, headings, pricing and FAQ text are all server-rendered. Only navigation is client-assembled.

Googlebot renders JS and will follow these. **GPTBot, ClaudeBot, PerplexityBot and OAI-SearchBot do not execute JavaScript.** To them, the homepage is a leaf node linking only to a contact page. Given the AI-search weighting in this audit, that compounds H1: the two highest-value commercial pages have neither a working sitemap discovery path for Google nor a crawlable link path for AI engines.

- **How would we know this failed?** `curl -s https://digitaloperations.co.za/doqix/ | grep 'href="products.html"'` returns nothing today. It must return a match.
- **Fix:** add static `<a>` links in a server-rendered footer block outside the JS-injected containers.

### H3. `products.html` has no structured data

The primary catalogue page selling five named SaaS products carries zero JSON-LD. Ready-to-paste `ItemList` + `SoftwareApplication` markup, built only from prices actually displayed on the page, was generated during this audit and is available on request.

### H4. `header.js` is render-blocking on both main pages

```html
<script src="js/header.js?v=0.12.10">
```

No `defer`, positioned before `<main>`. It is the sole exception among nine page scripts — every other one is deferred. The parser must fetch and execute 6,351 bytes before reaching the hero.

Note the injected header is `position: fixed` and `<main>` carries static `pt-20`, so this is **not** a CLS risk — only a render-path delay.

### H5. Three statistics carry no attribution

On the homepage, with no linked source, publisher or date:

- "Research shows professionals spend nearly 30% of their work week on manual, low-value tasks"
- "Most clients reclaim 8-15 hours a week within the first month"
- "One client cut R20,000/month in preventable data errors alone"

`htmldate` returns `publication_date: None` for the homepage — no machine-detectable freshness signal. Unsourced statistics are the weakest possible material for AI answer engines, which prefer attributable claims, and they cut directly against the Trustworthiness dimension that Google weights highest.

### L1. The site reads as a service-area business, not a hybrid

There is **no street address, suburb or postal code anywhere** on any page, in HTML or JSON-LD. Only `addressLocality: Cape Town`, `addressRegion: Western Cape`, `addressCountry: ZA`. There is also no Maps embed, no directions link, and no place link.

A locality-only address is functionally a service-area declaration, not proof of visitable premises. Meanwhile `areaServed` is set to the whole of South Africa, which is broader than a Cape Town map-pack goal implies.

**This is the decision that gates everything else local**, and only the owner can answer it: *does Do.Qix have a fixed, client-visitable Cape Town address?*

- **If yes:** publish the full street address and postal code, add `geo` at 5-decimal precision, embed a map on the contact page, configure GBP as a hybrid listing with the address shown. Proximity is the single largest component of local-pack ranking, and right now Google has no address to measure proximity from.
- **If no:** that is perfectly legitimate for a consultancy. But then say so in copy ("serving Cape Town and the Western Cape"), configure GBP explicitly as a service-area business with a defined suburb list, and narrow `areaServed` accordingly. The current ambiguous middle serves neither model.

### L2. The contact page carries no NAP schema

`contact.html` has `FAQPage` schema **only**. No `PostalAddress`, no `LocalBusiness`, no `ContactPoint`. The one page whose entire purpose is delivering NAP has none of it in machine-readable form, which is exactly what citation tools and validators scrape.

### L3. Phone formatting is inconsistent

Visible text uses `+27 61 514 8375`; JSON-LD and the `tel:` link use `+27615148375`. Same number, so not a data conflict, but directory import tools and NAP checkers do exact-string matching and will register a mismatch.

### L4. `sameAs` is an empty array

No LinkedIn, no Facebook, no GBP place URL. This is the cheapest available entity-corroboration signal and it is currently unused. A LinkedIn Company Page is close to mandatory for B2B consultancy credibility.

### L5. Testimonials undercut the local story

Only 2 of 7 testimonials are Cape Town (the rest are Pretoria, Durban, Johannesburg, Stellenbosch, Sandton). Good for a national narrative, working against a Cape Town map-pack push.

### L6. GBP name field warning

The contact page `<title>` is "Free Automation Consultation | Do.Qix Cape Town". Fine as an HTML title. **Do not copy that into the GBP business name field** — it must be exactly "Do.Qix". Google penalizes keyword-stuffed GBP names.

### Citation targets that actually matter in South Africa

BBB does not operate in South Africa and Yelp has negligible SA penetration — skip both. Relevant instead: Google Business Profile, Bing Places, Apple Business Connect, LinkedIn Company Page, Yellow Pages South Africa, Brabys, Snupit, Hotfrog SA, Cylex SA. For B2B software specifically: Clutch, GoodFirms, Crunchbase, G2. For local authority: Wesgro, Cape Chamber of Commerce, Silicon Cape.

This is a prioritized target list, **not** a verified presence audit — no citation index was available this run.

## The structural constraint

Worth stating separately, because no item above fixes it.

For the three query clusters these pages target, the result sets are dominated by consultative service pages with named clients and years-in-business signals, plus a substantial 33-44% share of guides, "best X" listicles, and directory/comparison pages. Do.Qix has zero pages of the second type.

An 8-page site with no blog, at a subpath of a domain with no established organic history, cannot compete for roughly a third of that real estate. Persona scoring puts the Comparison Shopper and the Risk-Averse Buyer tied at 37/100, both rated Critical Mismatch, while the locally-grounded and budget-conscious personas score 77 and 79 — the site is genuinely good at the things it addresses, and silent on the rest.

The homepage is also structurally a SaaS landing page (hero → pain → 3-step → pricing → testimonials) competing in a SERP where the modal type is a service page. `services.html` is the one page whose structure matches what Google rewards.

This is a content-architecture and authority gap. Meta-tag and schema work will not close it.

**How would we know this is wrong?** If any existing page reaches the top 20 for a cluster-1 or cluster-3 keyword within 90 days with no new content added, the assessment is too pessimistic.
